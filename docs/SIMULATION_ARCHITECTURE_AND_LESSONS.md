# RoomMind 开放式多人仿真：架构演进、问题与经验总结

本文记录 RoomMind 从可配置多角色对话原型发展为可运行、可比较、可评价的开放式多人仿真系统的过程。内容用于系统维护，也可作为论文中“系统设计”“设计迭代”和“有效性威胁”的素材。

重大架构调整的逐轮索引见 `docs/ARCHITECTURE_ITERATION_HISTORY.md`。该索引在每次重大架构调整后追加，本文继续承担总体架构与跨轮经验总结。

## 1. 初始研究目标

RoomMind 的目标不是生成一段“看起来像角色扮演”的文本，而是模拟多人商务与组织情境中的持续互动。场景不限于谈判，还包括产品决策、招聘面试、事故指挥、跨部门协作、客户沟通和其他开放任务。

系统希望把传统大模型群聊扩展为：

- 多个具有独立身份、职责、目标、倾向和私有信息的参与者；
- 独立记忆与反思，而不是一份中央共享记忆；
- 基于职责、提及和议题的发言调度；
- 可配置的任务状态、阶段、权限和完成条件；
- 可追踪的世界事件、对话、状态变化和模型调用；
- 人类参与模式与 AI 对 AI 测试模式；
- 与中央提示词式多角色 Baseline 进行受控比较；
- 对话生成、自动评价和人工盲评分离。

## 2. 当前总体架构

```text
场景定义
  ├─ 公共背景、参与者和任务结构
  ├─ 角色身份、职责、权限、私有状态
  ├─ 阶段、状态字段、完成条件
  └─ Dispatch Rules
        ↓
共享世界时间线 ───────────────┐
        ↓                     │
每个角色独立执行              │
感知 → 检索 → 决策 → 行动 → 反思 │
        ↓                     │
公开发言与世界事件             │
        ↓                     │
状态与事件评价器               │
        ↓                     │
任务状态 + 工作项 + 事件账本 ────┘
        ↓
进展检测与收敛控制
        ↓
继续 / 完成 / 有条件完成 / 延期 / 失败 / 停滞
```

核心原则是把“语言生成”与“仿真状态变化”分开。角色可以自由表达，但只有经过证据、类型、权限和条件验证的事件才能改变共享世界。

## 3. 系统演进阶段

### 3.1 从普通角色提示词到结构化角色

早期版本主要依赖 persona prompt。后来将角色拆为：

- identity/persona；
- responsibility；
- behavioral tendency；
- private state；
- protected secrets；
- redlines；
- authority（可提议、可确认、不可承诺）；
- relationship/team/interaction role。

经验：语言风格不能代表角色真实性。角色必须具有利益、知识边界和行动权限。

### 3.2 引入 Stanford Generative Agents 循环

每个角色拥有独立 memory stream，并执行：

```text
Seed Memory → Initial Plan
Perceive → Retrieve → React → Act
importance threshold → Reflect
```

共享的只有公开世界时间线；角色私有状态、计划、检索结果和反思不直接共享。

经验：独立记忆提高了角色差异，但也会产生“每个角色局部合理、会议整体不收敛”的新问题，因此仍需要共享的程序性治理层。

### 3.3 参与模式与测试模式

- Participation：真人作为玩家，NPC由AI生成。
- Test：玩家也由AI生成，自动推进对话。
- Baseline：中央提示词控制多个角色，不使用RoomMind独立记忆、状态治理和调度机制。

所有模式统一记录 speaker id/name/type/source、turn、sequence、content、时间和会话信息。

经验：AI玩家不能伪装成普通真人消息。必须用 `speaker_source=ai` 明确标记，同时在比较实验中保证双方使用同一公共信息和同一玩家策略。

### 3.4 状态、阶段与权限验证

系统引入 schema-driven task state：

- 类型化变量；
- proposed/disputed/confirmed/rejected；
- 精确公开引文证据；
- 提议与确认权限；
- 跨轮累积确认；
- 单调阶段推进；
- 显式完成条件。

经验：不能仅凭模型说“agreed”就更新状态。状态抽取必须与生成模型分离，并验证说话者、引文、字段类型和角色权限。

### 3.5 批量实验与受控Baseline

批量系统支持：

- 选择场景和条件；
- 每种组合重复多次；
- 固定模型、公共信息、AI玩家策略和随机顺序；
- 后台运行，不依赖页面保持打开；
- CSV/JSON/完整对话/调试包导出。

经验：Baseline不能故意弱化。它应获得相同公共背景、参与者和任务说明，只缺少待验证的RoomMind机制。否则比较结论没有效度。

### 3.6 对话生成与评价解耦

最初自动评价属于对话运行的一部分，评价超时会让整组实验失败。后来拆为：

1. 冻结并保存对话；
2. 独立启动AI评价；
3. 可选人工盲评；
4. 生成最终证据报告。

经验：后验观察者不能影响生成、停止或任务状态。评价失败只能形成缺失值，不能把成功对话标记为失败或低分。

## 4. 重要问题、根因和解决办法

### 4.1 `finish_reason=length` 导致空内容和 502

**表现：** 测试模式长对话时出现 `LLM API returned no visible content`，后端异常退出，前端显示 `ERR_EMPTY_RESPONSE` 或 `Failed to fetch`。

**根因：** 推理模型在较小 token 预算内将输出预算消耗在 reasoning，最终 `message.content` 为空；同时长对话提示不断增长。

**解决：**

- LLM客户端识别空content和length finish；
- 使用更高预算或紧凑提示重试；
- 只保留有限近期对话和结构化状态摘要；
- 玩家与NPC输出分别限制长度；
- 后端捕获异常并返回可诊断错误，不让连接无响应；
- 增加resilience smoke tests和模型调用日志。

### 4.2 内部计划泄漏为公开台词

**表现：** 角色将 `Focus on ...` 等内部计划原文说给用户，并在多个回合重复。

**根因：** 初始计划生成失败后保存了fallback boilerplate；无人发言时，强制回复路径把active plan直接作为公开草稿。

**解决：**

- 原始计划永不直接作为台词；
- speech safety拒绝计划回声、私有标记和截断句；
- 计划生成失败时重试并记录fallback质量；
- 别名与名字提及识别；
- 记录fallback_speak和decision preview用于调试。

### 4.3 测试模式对话无限增长

**表现：** 一些RoomMind会话达到50轮上限，反复要求文件、确认或下一步。

**根因：**

- “我会提供文件”只是语言，没有成为可执行世界事件；
- 系统无法区分承诺提供与已经提供；
- 每个角色从自身计划出发局部合理，但没有全局收敛账本；
- 比较协议曾禁用停滞终止；
-完成条件只接受全量成功，缺少延期、交接和失败等现实结局。

**通用解决：**

- 增加domain-neutral event ledger；
- 区分 artifact_offered 与 artifact_submitted；
- 记录 information、action、decision、blocker、handoff、schedule 和 outcome；
- 以“状态/工作项是否实质变化”而非新措辞判断进展；
- 重复承诺不重置停滞计数；
- 停滞窗口对测试和比较模式均生效；
- 支持 completed/conditional/deferred/failed/stalled；
- 提醒拥有材料或行动权限的角色立即给出具体事实或执行动作；
- 无法在当前会话完成时，要求现实的交接、后续日程或明确关闭。

### 4.4 多角色每轮都发言，造成重复

**表现：** 玩家只询问一个角色，其他角色仍重复自己的立场。

**根因：** 相关性被等同于发言必要性；fallback保证回复但没有“新增贡献”门槛。

**解决：**

- 直接提及和dispatch决定优先级；
- 增加contribution gate：只有回答直接问题，或提供新事实、提议、反对、决定、行动、协调时才发言；
- 已确认事项不重新打开；
- 没有新增价值时选择wait；
- 对语义重复和动作签名进行后续监测。

### 4.5 评价系统全部失败但模型其实返回正确JSON

**表现：** 六维AI评价显示unusable response，原始预览却包含合法 `dimension_score` 和 `metrics`。

**根因：** 解析器把规范响应内部的 `metrics` 错当成外层包装并解包，丢失顶层 `dimension_score`。

**解决：**

- 只有在顶层没有分数、且metrics本身确实包含分数时才解包；
- 增加规范响应回归测试；
- 保存response preview和per-dimension errors；
- 对话生成与评价分离，允许只重新评价冻结对话。

### 4.6 评价偶发失败

**表现：** 相同对话部分维度有时成功、有时失败。

**根因：** 大模型结构化输出存在格式波动、输出截断、超时和过量证据编号。

**解决与待改进：**

- 每个维度独立评价与超时；
- 限制证据数量和理由长度；
- 对length/invalid JSON进行紧凑重试；
- 保留原始响应与错误分类；
- 后续应支持只重试缺失维度，并保存评价版本而非覆盖历史。

### 4.7 Baseline看起来得分更高

**表现：** 初步单次结果中Baseline在时间连贯性和程序真实性上高于RoomMind。

**解释：** Baseline通常4–9轮快速结束，RoomMind可能运行20–50轮。短对话更少暴露矛盾，也可能通过过早完成获得表面高分。

**方法学处理：**

- 将premature completion作为独立有效性指标；
- 同时报告对话长度、状态达成和终止原因；
- 不把“短且无矛盾”等同于真实；
- 多次重复并采用配对统计；
- 加入人工盲评；
- 分析长度匹配或以固定观察窗口做敏感性分析。

## 5. 开放场景的通用仿真状态

新版task state同时包含四类信息：

```json
{
  "variables": {},
  "work_items": {},
  "event_ledger": [],
  "outcome": {},
  "progress": {}
}
```

### 5.1 Variables

场景作者定义的类型化结果，例如价格、准备度、事故范围、面试证据或责任人。

### 5.2 Work items

从公开对话中抽取的材料、行动、决定、阻塞、交接或日程。场景无需预先枚举所有工作项。

### 5.3 Event ledger

事件必须包含当前轮公开发言的精确证据。允许类型：

- information_provided；
- artifact_offered / artifact_submitted / artifact_reviewed；
- action_committed / action_completed；
- decision；
- blocker；
- handoff；
- schedule；
- outcome。

### 5.4 Outcome

开放场景允许：

- completed：配置目标完成；
- conditional：有条件完成；
- deferred：延期等待外部条件；
- failed：明确失败或终止；
- stalled：系统检测到长期无实质进展。

## 6. 为真实性服务的设计逻辑

1. **角色真实性**：身份、职责、利益、倾向和权限保持一致。
2. **认识真实性**：角色只使用其私有知识和已经公开的信息。
3. **时间真实性**：已经发生的事实、决定和行动进入持久账本。
4. **互动真实性**：发言由提及、职责、议题和新增贡献共同决定。
5. **多人真实性**：每个角色有独立记忆和计划，但共享同一公共世界。
6. **程序真实性**：提议、确认、行动、交接和结局受到权限与证据约束。
7. **收敛真实性**：真实会议不一定成功，但必须能够完成、延期、失败或明确交接，而不是无限聊天。

## 7. 评价框架

RoomMind当前围绕六个真实性维度组织AI评价与人工盲评：

1. Role & strategic fidelity；
2. Information boundary / epistemic fidelity；
3. Temporal coherence；
4. Interaction structure fidelity；
5. Multi-party dynamics fidelity；
6. Procedural fidelity。

评价者是对话之外的观察者，不参与生成或停止。论文应分别报告：

- 六维评分及细分指标；
- 确定性日志指标；
- 任务结局与终止原因；
- 对话长度和模型调用稳定性；
- AI评价缺失率；
- 人工盲评及评审者一致性。

## 8. 当前有效性威胁

- AI评价者的格式稳定性和评分偏好；
- 单次运行样本过少；
- RoomMind与Baseline对话长度不一致；
- 第8轮以前的Baseline为集中式多角色模型，第8轮以后为传统独立智能体；
  两种协议的数据不得混合；
- 模型非确定性；
- 场景配置质量影响系统表现；
- 自动状态抽取仍依赖LLM；
- 语义重复检测仍需加强；
- 工作项是从公开语言抽取，并不等同于连接真实外部工具后的执行。

## 9. 后续优先事项

1. 对事件抽取准确率进行人工标注验证；
2. 增加语义动作级重复检测；
3. 评价只重试失败维度并保留版本历史；
4. 为工作项增加可选工具/数据源执行器；
5. 对不同类型场景建立通用终止策略测试集；
6. 多次重复、配对统计和人工盲评；
7. 在导出中单独呈现event ledger、work items和outcome轨迹。

## 9.1 第7轮更新：事件语义规范化

基于批次`c532e2e7-078e-446c-bbaf-3097e20aa384`的forensic debug bundle，系统将task state升级为schema v4：

- promise/proposal不再构成持久进展；
- information、outcome等事件具有确定工作项状态；
- 工作项使用稳定键、别名和近似归并；
- artifact review必须发生在artifact submission之后；
- 只有required且未解决的工作项进入open issues；
- 明确闭会语言直接形成终局；
- AI玩家优先回答本轮最新直接问题。

此次更新把第6轮的“存在治理层”推进为“治理层具有可验证状态转换约束”。

## 9.2 第8轮更新：传统独立智能体对照

Baseline改为每个NPC独立模型调用、独立角色提示、独立私有资料和按角色保存的
普通滚动公开对话记忆。它不拥有RoomMind的observation、reflection、planning、
语义记忆检索、dispatch、authority enforcement、task state、event ledger、
evidence gate和completion governance。

这一设计使主要研究问题变为：

> 当各角色已经是具有普通对话记忆的独立传统智能体时，RoomMind的结构化认知
> 与治理机制是否进一步提升多人仿真的真实性、一致性和程序可靠性？

协议标识更新为`roommind-vs-independent-memory-agents-v3`。所有最终论文批次
必须使用该协议重新生成，旧的集中式Baseline仅可作为探索性或辅助结果。

## 10. 核心经验

RoomMind开发过程最重要的认识是：

> 多个角色分别说出合理的话，并不自动构成真实的多人仿真。真实性需要角色独立性、信息边界、共享世界状态、权限约束、可执行事件、程序推进和自然收敛共同成立。

系统优化的方向因此不是继续堆叠更长prompt，而是让每次发言能够被验证、转化为世界事件、影响后续行为，并最终形成可解释的结局。

## 11. 第32轮更新：G4.0有界议程收敛

G3.9的冻结实验表明，继续增加确认短语并不能解决多人会议的整体真实性：
两个RoomMind场景仍然停滞，所有端到端quote confirmation计数为零，且共享玩家
能够接受不符合公开目标的中间方案。G4.0因此开始新的大代际，重点从“识别更多
说法”转向“约束会议如何推进和结束”。

- 同一角色的高相似度重复请求或承诺由确定性边界拦截；
- 对RoomMind和Baseline的共享玩家同时强调公开目标阈值，保持比较公平；
- 无进展不再自动等同技术故障，而是保留未决事项并形成conditional/deferred结局；
- `stalled`保留给安全上限或技术耗尽，防止混淆业务未决与系统失败；
- 新增重复抑制、治理收尾和冻结对话复算探针。

这次调整不删除斯坦福生成式智能体的独立记忆、计划、感知、检索、反思和行动
循环；治理层仍只协调公共世界，不共享角色私有记忆。
